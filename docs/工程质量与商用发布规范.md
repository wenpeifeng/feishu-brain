# 飞书知识问答：工程质量与商用发布规范

版本：1.0  
适用范围：检索、聊天召回、证据排序、回答生成、引用展示、质量评测、开发者设置、权限与前端交互。

## 0. 规范来源与继承关系

仓库当前及 Git 历史中没有项目级 `CLAUDE.md` 或 `.claude/rules`。可继承的上一阶段工程约束主要来自：

- `docs/superpowers/specs/2026-07-14-feishu-kb-qa-design.md`
- `docs/superpowers/plans/2026-07-14-feishu-kb-qa-v1.md`

本规范继承并强化了其中这些有效要求：接口先定义、测试先失败再实现、每任务独立验证、用户 token 权限边界、对话 owner 强校验、密钥不下发、外部服务失败降级、SSE 事件契约和分阶段交付。

以下旧设计不再作为现行规范：服务端内置模型密钥、把敏感字段放入通用配置、仅用 mock/单一手工问题作为验收、固定厂商/模型列表、只验证功能成功而不验证精度与性能。现行规则以根目录 `AGENTS.md` 和本文为准；旧文档只作架构历史参考。

## 1. 目标与原则

系统优化的目标不是让某一句测试问题“看起来答对”，而是在未知问题、未知项目名、错别字、不同资料类型和不同屏幕下仍保持稳定、可解释、可回归。

所有方案必须同时满足：

- 可泛化：机制解决一类问题，不绑定单个业务词。
- 有证据：结论来自自动测试、真实链路数据或人工金标，不来自主观推断。
- 可回退：外部 API、模型或法官失败时有明确降级，不把未验证候选冒充高质量证据。
- 可解释：能说明某条为何召回、为何入选、为何进入“更多相关”。
- 可运营：真实问题自动进入质量工作台，经人工标注后才能驱动参数建议。
- 可隔离：模型设置、调试参数、质量案例和业务数据按用户或明确管理员边界隔离。

## 2. 禁止单例硬编码

### 2.1 禁止项

生产代码不得出现以下形式的修复：

- `if (question.includes('某项目')) ...`
- 在源码中维护“错字 → 业务专名”映射来修一个线上问题。
- 按某篇文档标题、某个人名、某个固定日期提升或降低排名。
- 为通过测试给某个 token、URL 或 case id 特殊加分。
- 发现模型误判后直接把该答案字符串写进提示词。

业务专名、真实问题和期望证据应放在金标/回归数据中。唯一允许的词典是独立配置或自动学习的数据资产，且必须有来源、作用域、版本、更新时间和回滚能力；不得藏在算法源码中。

### 2.2 修复前必须回答四个问题

1. 这是哪一类失败：漏召回、错召回、上下文窗口缺失、时效倒置、冲突未识别、生成不忠实、引用错位，还是 UI 展示错误？
2. 除当前 case 外，至少两个不同实体如何触发同类问题？
3. 通用方案可能误伤什么反例？
4. 用什么指标和测试证明收益大于损失？

没有这四个答案，不进入实现。

## 3. 查询理解与错别字处理

### 3.1 商用链路

查询处理采用“原词保留 + 高置信模型规划 + 语料校验”的组合：

1. 原始问题永远进入召回，不能被纠错结果替换。
2. 当前用户选择的模型生成关键词、可能的纠错和实体扩展。
3. 只有高置信纠错才作为补充查询；低置信模型猜测直接丢弃。
4. 低置信时，从该用户本次有权限看到的文档标题和聊天结果中发现近似实体，再补充检索。
5. 补充实体只扩大候选池，不能直接绕过向量门槛和相关性法官。
6. 查询规划按“模型版本 + 原问题”缓存；缓存切换模型后自然失效。

### 3.2 为什么不能只用模型

通用模型不了解所有公司内部简称。它可以纠正常见错字，也可能把内部专名改成另一个合法普通词。因此模型只能提出候选，企业语料才是专名真实性依据。

### 3.3 必测场景

- 常见同音/形近字错误。
- 正确专名，不得被过度纠正。
- 内部简称与正式文档名不同。
- 两个都合法但含义不同的词，不得擅自合并。
- 中英文缩写、大小写、空格和全半角差异。
- 纠错服务失败或低置信时，原查询仍能完成召回。

## 4. 文档与聊天召回

文档和聊天不能使用完全相同的候选构造方式：

- 文档：检索标题与正文，读取预算内同时保留相关度和新鲜度席位。
- 聊天：命中问句时必须携带同一会话后续回复；以消息窗口为候选，避免只拿到高相似问题、丢掉真正答案。
- 重复窗口：上下文消息 id 有交集时去重，不能重复占用证据位。
- 来源融合：聊天和文档均先宽召回，再统一进行语义精排与相关性准入；不能因来源排列顺序挤掉另一类资料。
- 状态问题：同等相关时优先明确、完整、更新的状态证据；局部文档“未提到”不得推导为项目整体“不存在”。

## 5. 相关性、排序与展示

### 5.1 分数职责

- 向量/BM25：负责宽召回和初排，不代表最终置信度。
- LLM 法官：负责是否相关的准入门槛，不把 3 分自动解释为比 2 分更适合作答。
- 证据质量排序：在过闸后综合直接性、完整性、时效、冲突、近重复和分数断层。

### 5.2 Top K 语义

系统必须区分三个数量：

- 召回池：为保证 Recall 而扩大，不能直接展示为证据。
- 主证据：实际发送给回答模型，并与正文 `[n]` 编号严格一致。
- 更多相关：通过相关性准入但未进入主证据的全部结果。

同一次回答中，所有过闸结果必须属于“主证据”或“更多相关”，不得静默丢失。页面默认展示主证据；“更多相关”完整可展开。它们没有参与本次回答，文案必须明确。

## 6. 时效与冲突

- 资料标题或消息时间必须进入生成上下文。
- “本周、下周、明天”等相对时间按资料产生日期换算为绝对日期。
- 已经过期的计划只能写“原计划于……；是否完成暂无更新”，不得表述成当前仍待发生。
- 新旧资料是正常演进时采用更新状态；同日或同阶段出现互斥结论时展示冲突提示。
- 不得用文档更新时间冒充业务发生时间；优先使用内容日期或消息时间。

## 7. 人工金标与参数发布

### 7.1 自动采集

每次真实检索自动记录：问题、模型版本、候选轨迹、向量分、法官结果、证据质量分、主证据、更多相关、答案、置信度、冲突和用户反馈。不得记录 API Key 或访问令牌。

优先级自动提升条件：点踩、无结果、冲突、中置信或存在较多边界证据。

### 7.2 人工标注

人工需要标注：答案正确/部分正确/错误/资料不足，以及每条候选相关/无关/不确定。未经人工确认的自动判断不称为金标。

### 7.3 参数建议门槛

少于 30 个已标问题或 100 条已标候选时，不生成参数推荐。达到门槛后至少报告 Precision、Recall、F1、平均主证据数及当前基线对比。推荐值只进入 A/B，不能自动覆盖线上默认。

参数变更必须记录：数据集版本、样本量、旧值、新值、指标变化、延迟变化、发布人和回滚值。

## 8. 前端规范

- 内容层级固定为：回答 → 主参考 → 更多相关 → 免责声明/操作 → 输入框。
- 单行标题必须 `min-width: 0`、省略号和容器边界同时成立；不能靠页面横向滚动查看。
- 更多相关展开/收起要有高度与透明度过渡，动画中间态可测，`aria-expanded` 与视觉状态一致。
- 390px 移动端优先保证正文与引用可读宽度；作者、日期等次要信息可隐藏，但来源标题不能消失。
- 所有修改至少覆盖 1920、1440、1280、1024、768、390 六个断点。
- 自动几何测试通过后仍需复核一张桌面和一张移动截图；不能只凭 DOM 数字宣称视觉正确。
- 设置项使用用户能理解的文案和问号说明。实验性开关明确标注风险；系统默认可一键恢复。
- 图标必须按使用场景建立语义组件，不能把空状态插画、大尺寸资源直接塞进菜单或按钮。菜单组件统一约束图标槽、行高、文字起点和焦点态；新增一项时回归全部同级项，而不是只看新增项。

## 9. 安全与权限

- API Key 只在服务端会话使用，GET 配置仅返回 `hasKey`，不返回明文。
- 检索参数默认按登录会话隔离，不允许普通用户修改全局默认。
- 质量案例默认只显示本人；组织视图只聚合同一飞书 `tenant_key` 下已接入成员的数据，仅组织 Owner/管理员可见。`ADMIN_OPEN_IDS` 只用于已有部署首次迁移引导，后续角色在组织管理页维护。
- 所有资源读取使用当前用户 token，保持飞书原始权限边界。
- 日志和质量数据不得包含访问令牌、刷新令牌、应用密钥或模型密钥。

## 10. 测试矩阵

每类改动的最低验证如下：

| 改动 | 必须验证 |
|---|---|
| 查询理解/纠错 | 原 case、不同实体泛化、合法词反例、低置信回退、缓存 |
| 聊天召回 | 问句命中后续答案、跨话题间隔、窗口去重、纠正消息 |
| 排序/Top K | 同档断层、最新状态、局部否定、冲突、主/更多全集守恒 |
| 生成/引用 | 核心结论、引用存在、编号不越界、时效表达、禁用资料式开场 |
| 配置/权限 | 双用户隔离、默认拒绝、恢复默认、密钥不回传 |
| UI | 六断点、溢出、省略号、动画中间态、移动端截图 |
| 性能 | 搜索、读取、向量、法官、首字、总耗时分阶段记录 |

禁止通过删除断言、放宽为“任意相关即可”、只测 mock 不测真实链路等方式制造假通过。

## 10.1 缓存准确性规范

缓存必须按“是否包含事实或模型判断”分类，不能统一讨论冷热：

| 缓存类型 | 生产策略 | 准确性要求 |
|---|---|---|
| 最终答案 | 禁用 | 每次事实问题重新检索和生成；不得回放旧答案 |
| 飞书检索结果/正文 | 生产禁用；fixture 仅离线评测 | 在线必须读取当前用户最新可见资料；fixture 结果不得用于生产结论 |
| Embedding | 允许长期缓存 | key 必须含端点、模型和完整原文 hash；任一变化自动失效 |
| 查询纠错/意图/改写 | 短 TTL | key 含端点、模型、算法版本和输入；错误不得永久固化 |
| 法官/对抗复核 | 短 TTL | key 含端点、模型、prompt 版本、问题和证据 hash；过期重判 |
| OAuth/app token | 仅按官方过期时间 | 提前刷新；不得与业务答案缓存混用 |
| UI 临时事件 | 仅当前回答生命周期 | 页面刷新或新问题后清空，不写入事实缓存 |

规则：

- 在人工金标与重复运行稳定性达标前，模型决策缓存默认关闭；验证收益后才可通过服务端环境变量显式开启，旧版无时间戳条目一律失效。
- 修改 prompt、评分语义、模型端点或算法时必须升级缓存版本；不能只依赖 TTL。
- 点踩/人工纠错后，相关问题的决策缓存必须能够定向失效；在该能力完成前，点踩 case 的线上复测使用冷决策缓存。
- 冷缓存精度测试必须绕过所有模型决策缓存；热缓存只用于验证结果一致性和性能收益。
- Embedding 热缓存不能替代检索实时性验证，因为它只复用向量计算，不能证明资料仍是最新事实。

## 11. 技术方案证据门禁

任何影响召回、排序、法官、生成、引用、缓存、权限或关键交互的方案，在进入生产代码前必须建立实验记录。禁止用“业界常用”“模型应该能识别”“理论上更准”代替本项目证据。

### 11.1 实验记录必填项

每项关键优化必须记录：

| 字段 | 要求 |
|---|---|
| 问题与根因 | 提供真实失败样本、当前链路轨迹和可复现步骤 |
| 可证伪假设 | 写成“若采用 X，则指标 Y 在数据集 Z 上提升且指标 W 不退化超过阈值” |
| 基线 | 固定代码版本、模型、参数、数据集版本和冷/热缓存状态 |
| 候选方案 | 至少包含“不修改”对照；重大算法变更应比较两个以上可行方案 |
| 数据 | 人工金标数量、候选数量、来源分布、时间范围、难例/反例占比 |
| 精度结果 | Recall@K、Precision@K、MRR/nDCG、证据 F1、答案正确率、引用正确率 |
| 稳定性 | 同一输入重复运行结果一致率、外部服务失败率、降级路径正确率 |
| 性能成本 | 分阶段 p50/p95、首字/总耗时、模型 token、API 次数和缓存命中率 |
| 安全影响 | 数据作用域、跨用户隔离、敏感信息、默认拒绝与审计日志 |
| 结论 | 通过/拒绝/继续实验，并列出证据链接、限制、负责人和日期 |
| 发布回滚 | 灰度范围、监控阈值、自动/人工回滚条件和恢复值 |

没有完整记录的方案只能作为原型，不得标注“已优化”或进入默认开启状态。

### 11.2 算法变更的多维验证

算法优化不能只看当前 case 是否命中，至少同时覆盖：

- 召回：目标证据是否进入候选池，Recall@K 是否提升。
- 精准：无关证据、跨项目证据、局部否定是否被抑制。
- 排序：直接答案、最新状态、完整上下文是否排在弱线索之前。
- 生成：答案是否忠实、是否遗漏、是否误用历史计划。
- 引用：每个结论是否有来源，编号是否越界，来源是否真的支撑该句。
- 泛化：至少两个不同实体、不同资料类型、不同错字类型。
- 反例：正确专名不被纠错；合法歧义不被强行合并；低置信失败能安全回退。
- 稳定：冷缓存与热缓存各测；相同输入至少重复 5 次，记录候选/排序一致率。
- 性能：不能只报平均值；必须分阶段和报告 p95。
- 成本：新增模型调用或补查必须量化，说明收益是否值得。

任何一个关键维度显著退化，方案不得直接发布；需要重新设计或进入受控实验开关。

### 11.3 数据集分层

评测集至少分为：

1. 核心金标：真实高频问题，人工逐条确认答案与证据。
2. 历史回归：所有线上失败和用户反馈 case，只增不删。
3. 泛化集：换实体、换表达、换资料来源验证机制可迁移。
4. 对抗/反例集：错别字、否定、纠正、冲突、过期计划、同名不同项目。
5. 无答案集：验证拒答和“更多相关”不会制造答案。
6. 性能集：短问、长问、多轮、文档多、聊天多、冷缓存。

调整参数时冻结评测集；不得看到测试结果后修改金标来迎合方案。训练/调参与最终验收数据应分离。

### 11.4 生产灰度与观测

- 新算法默认先以 shadow 模式记录结果，不影响用户答案；与当前基线做逐请求对照。
- shadow 达标后按用户或会话小流量灰度，不能随机混用证据编号或缓存。
- 线上必须记录阶段耗时、候选数、过闸数、主证据数、更多相关数、降级原因、模型版本和参数版本。
- 监控至少包含：失败率、无结果率、点踩率、引用点击率、p95 首字、p95 总耗时、模型/API 成本。
- 达到回滚阈值立即恢复上一个已验证基线；实验数据保留用于根因分析。

## 12. 性能与商用结论

性能优化不能用减少正确证据来换取。先记录阶段耗时，再处理最大瓶颈；无数据不得猜测。

单次耗时只能用于诊断，不能宣称 SLA。商用性能结论至少需要 30 次代表性请求，报告 p50、p95、失败率、首字耗时和总耗时，并区分缓存冷/热。精度结论必须使用冻结的人工金标集。

在人工金标未达到门槛前，系统只能标记为“技术基线通过”，不得标记“已证明最优”或“商用精度达标”。

- [ ] 生产代码无业务专名/固定日期/特定 token 特判。
- [ ] 原失败、泛化和反例测试齐全。
- [ ] 冷/热缓存与重复运行稳定性已验证。
- [ ] 精度、召回、排序、生成、引用、性能、成本和安全均有数据。
- [ ] 全量单元与集成测试通过。
- [ ] 真实检索和完整回答链路通过。
- [ ] 引用编号、主证据与更多相关全集一致。
