# 关键升级与优化（大白话版：为什么做 → 怎么做 → 价值）

> 一条主线：**检索是这个产品的命根子**。答案错了、来源不可信，用户立刻就不信任了。所以下面每一步，都是围绕"**既要找得到、又不能找错**"在解决问题。

---

## 一、为什么要加"LLM 判官"

**问题**：一开始只用"向量相似度"给文档排序。但我实测发现，本嵌入模型算出来的分数，**相关的内容大概 0.55~0.76，不相关的也有 0.25~0.55，两者在 0.55 附近是重叠的**——光看分数根本分不清"真相关"还是"只是碰巧字面像"。再加上飞书搜索本来就会返回一堆"沾边"的文档。结果就是：一堆无关文档因为分数不低，被当成答案来源展示。

**怎么做**：在向量之上，再加一道**大模型判官**。把每篇候选交给大模型，问它一个很朴素的问题——"**这段内容到底有没有提供能回答用户问题的信息？**"，打 0~3 分，只留 2 分以上的。于是形成两道关卡：**向量负责"广撒网找出可能相关的"，判官负责"严格判到底答不答得上"**。

**价值**：无关文档被挡在展示之外。用一套多维审计去量化，**无关误报从 13 条降到 0**。

---

## 二、为什么还要"对抗式复核"

**问题**：判官虽好，但也不是 100% 准，大概 90~95%。它偶尔会对"话题相邻、沾了点边"的文档心软，给个 2 分放进来——最后残留的那几条误报，几乎都出在这种"2 分边界档"上。

**怎么做**：判 3 分的（很确定）直接信任；只对**2 分的边界档**，再换一个"**怀疑者**"的口吻重判一遍——"你别客气，仔细看它是不是真的回答了？拿不准就毙掉"。只有扛住这轮质疑的才留下。

**价值**：把最后偶发的那点误报也压到 **0**。而且只在"边界档"才触发，判 3 的高置信档不复核，不拖慢正常问答。

---

## 三、文档 和 消息，是两种不同的检索（这一点最关键）

**问题**：我们同时检索**文档**和**聊天记录**，但这两种内容形态完全不同：
- **文档**是"直接陈述"——里面通常就写着答案本身，向量 + 判官那套直接管用。
- **聊天记录**是"一问一答"——很多时候答案不在一条消息里。你搜"澳洲 redis 用哪个库"，**向量分最高、命中的那条往往是别人问的同一个问题**（"你们澳洲 redis 用哪个库？"），真正的答案（"redis-platform"）在**它后面的一两条回复**里。

如果对消息也只用"命中那一条 + 向量 + 判官"，判官只看到一句问题、没有答案，就会判"没信息"给丢掉——**答案明明在，却被丢了**。

**怎么做**：针对消息，不是单看命中的那一条。而是——**先用向量找出分数高的命中消息，再把它前后几条一起捞出来，拼成一小段完整的问答，再交给判官打分**。这样判官看到的是"问 + 答"，就能正确判断"这里有答案"。（前后各捞几条可在开发者设置里调；补太多会把后面跑题的闲聊也带进来、反而稀释，实测 2~3 条最合适。）

**价值**：聊天里的答案不再丢。实测"澳洲 redis 用哪个库"从"没找到" → 正确答出"redis-platform"；"澳储要交出去吗"从丢弃 → 正确答出"不交"。**用"补上下文"这一招，让同一套判官既能判文档、也能判聊天——不用为消息单独写一套算法**（本质是"喂给判官的料要完整"，而不是"换一套判断标准"）。

## 四、消息能定位到"具体那一条"（官方说没有，我们打通了）

**问题**：参考里引用了一条聊天记录，点进去只能**打开这个会话**，但**跳不到那一句**——用户还得自己在几百条消息里翻。对一个"答案要能溯源"的产品，这等于溯源断在了最后一步。

**卡点**：我专门去查了飞书官方文档、也问了官方技术人员，结论一致——**第三方应用生成"定位到某条消息"的深链，官方没有提供，接口参数里也找不到 position 这种东西**。按常规到这就该放弃了。

**那为什么还是敢试 `position`、又凭什么判断该传它**：不是瞎猜，是有两条线索推出来的——
1. **平台自己的数据模型里，"位置"这个概念是存在的**。我们调飞书的"拉取会话消息"接口时，**每条消息的返回里都带一个 `message_position` 字段**（它在这个会话里的第几条）。官方能返回它，说明它内部是认这个序号的。
2. **飞书客户端自己就有"跳到某条消息"的行为**——你在飞书里搜消息、点一条结果，它就是跳过去并高亮的。客户端的深链（`applink`）通常**能接受比官方文档写出来的更多的参数**。

把这两条合起来推断：**接口既然把 `message_position` 交给了我，客户端内部又认这个序号，那深链大概率能吃一个没写进文档的 `position` 参数**。于是把它拼到打开会话的链接后面 `client/chat/open?openChatId=X&position=N`，**拿真机一点**——真的跳转过去、而且**高亮**了那一条。**文档说没有 ≠ 能力不存在；客户端认不认，只有真机点一下才算数。**

**价值**（不止"能跳过去"）：
- **补齐了可信溯源的最后一公里**：从"帮你打开会话、自己去翻"升级成"直接跳到并高亮那句话"。对知识问答来说，答案能一键回到原话，可信度是质的差别。
- **一套可复用的方法论**：官方文档不是能力的边界，**实测才是唯一判据**。同一招后来又用在"分享到会话"上——先去试接口通不通，而不是先信"文档没写就是不行"。这是这个项目里反复奏效的工程习惯。

## 五、召回准确度的几个关键修复（每个都解决一类"找不到 / 找错"）

- **双路召回**：只让大模型抽关键词去搜，它有时会抽歪（丢词、甚至加了原句没有的词），导致真文档一篇都搜不到。**所以改成：关键词 + 用户原问题，各搜一次合起来**，互相兜底。
- **切块按相关度截断**（不按位置）：一篇大文档几十段，切块超上限时原来是"从头按位置砍"，结果**真正含答案的那段排在后面、被砍掉了**，文档分数虚低被丢。**改成按词面相关度排序再砍**，精准段必留。
- **向量层与对话模型解耦**：嵌入本来跟着"用户选的对话厂商"走，而用户会话里残留了个没配 key 的默认厂商，导致**整条链路悄悄退化成了纯词法、语义检索全废**。**改成：不管对话用哪个模型，向量层一律用固定的嵌入模型**，语义召回恢复。
- **垃圾根本过滤**：机器人自动发的消息、系统日志泄漏进群的内容，被检索当成参考。**改成按"是不是真人发的"从根上过滤**，而不是逐条堵。
- **阈值按实测数据定（0.40）**：网上常说余弦阈值设 0.7，但那是别的模型的经验值。**我实测了我们这个模型的分布，真答案就落在 0.55~0.66**，设 0.7 会把真答案全误杀，所以定在 0.40。

## 六、怎么保证"改好一个不会坏一个"

**问题**：检索这种东西，改一处很容易在别处引入新问题，改到后面自己都不知道有没有变差。

**怎么做**：建了两套自动化——**确定性评测**（固定题目，量化"该找到的有没有找到""有没有混入无关"）+ **对抗式多维审计**（一批各种类型的问题跑真实链路，再让一个独立的严格评审逐条判"展示给用户的每一条是不是真相关"）。**把"出现无关文档"这个失败本身，做成了每次改动都要过的回归测试**。

**价值**：每次优化都用数据说话——"召回变好了、误报没涨"才算数。靠这套，误报一轮从 13 压到 0。

---

## 七、自建知识库：把语义召回补在"我们自己的数据"上

**问题**：飞书文档只能关键词搜（平台限制），"测试环境"搜不到写"dev/pre"的文档，召回有天花板。飞书文档太多，也不适合我们去全量建索引。

**怎么做**：把检索分成**两条线**——飞书那条只能关键词、认了；但**用户上传的知识库是我们自己的数据**，在这条线上做全套稠密召回：上传即**切块 + 每块 embedding 建向量索引**，查询时 **BM25(字面) + 向量(语义) 用 RRF 融合**，两条线召回合并后共用同一套判官。

**价值**：自有数据这侧**语义召回打通**——实测上传内容只写"dev/pre"，用"开发/预发布环境"也能召回。平台管不了的召回质量，我在自建库这条线自己补齐了。

## 八、答不了 / 问偏了，怎么优雅接住（信任与体验）

**问题**：用户会问各种问题——常识("今天周几")、太笼统("有问题吗")、身份("你是谁")、以及"确实查不到的公司问题"。一刀切要么乱答、要么冷冰冰"没找到"。

**怎么做**：加了一层"**分流 + 兜底**"——
- **常识/寒暄**：轻分类器判为通用问题 → 直接简短答，不弹兜底。
- **太笼统**：完全没对象的先**反问补全**；带了具体名词的照常检索、不打扰。
- **确实没找到的公司问题**：**兜底卡**引导关注公众号留言 / 一键把问题提交给作者（进 bad-case 清单）。
- **身份/作者问题**：固定介绍 + 引导公众号。
- **多来源打架**：**冲突检测**在参考区上方黄条点明。
- **答案可信度**：复用判官分标**高/中置信 + N 篇佐证**，反幻觉可视化。
- **点踩闭环**：点踩追问"哪里不对"→ 沉淀"待改进"清单，形成质量飞轮。

**价值**：从"只会检索"升级成"**答得准、接得住、还能自我改进**"——这些都是商用最看重的信任与体验。

---

## 九、文档摄入：零依赖解析 Office / PDF

**问题**：上传只支持纯文本，Word/Excel/PPT/PDF 用不了，覆盖率是硬伤。

**怎么做**：**服务端解析、尽量零依赖**——Office(docx/xlsx/pptx)本质是 ZIP+XML，用 Node 内置 zlib 手写解析；文本 PDF 手写 FlateDecode + 文本算子抽取（都零 key）；图片/扫描件才走 OCR，且**没配 OCR key 只挡这一类、不影响其它上传**。

**价值**：常见办公文档一键入库、零依赖、免 key；贴合"缺哪个 key 只挡哪个功能"的原则。

---

## 一句话总结
**文档直接陈述、聊天一问一答，两种形态要区别对待**：文档靠"向量 + 判官"，聊天靠"命中后补前后几条上下文再判"。之上再叠一层"对抗式复核"保精度、一套"多维审计"防倒退。整体原则：**检索是核心，宁可找不到、也不能找错**。
