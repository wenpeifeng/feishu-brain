# 飞书企业知识问答系统 — 技术梳理（面试向）

## 一句话
企业内部的 RAG 问答：用飞书账号登录，**按你自己的权限**去搜**文档 + 表格 + 聊天记录 + 本地上传的知识库**，给出**带来源引用、能溯源、不编造**的答案。**纯 Node.js、零第三方库**，RAG 整条链路从零手写。

**为什么做这个**：公司知识全散在飞书里——关键词搜不到、搜到了也不知道可不可信、聊天里问过的答案更是沉不下来。自己从零做而不是套现成框架，是想**把检索的每一环真正吃透**，也为了贴合飞书那套"按人授权"的权限模型。

---

## 整体架构

**两条检索线，合流后共用一套精排**——这是全局最重要的一张图：
```
                         ┌─ 飞书检索：关键词搜文档/表格 + 会话检索（受平台限制，只有关键词）
理解问题 → 多路召回 ──────┤
                         └─ 自建知识库：上传文档切块+embedding → BM25 + 向量 RRF（有语义）
                                    │
        合并候选池 → 读正文 → 结构感知切块 → 向量粗排 → LLM判官精排 → 对抗式复核 → 生成带引用答案
```
一句话记住：**先广撒网找出"可能相关"（召回），再层层严判留下"真能回答"（精排）。两条线各自召回、合并成一个池子，之后共用同一套重排/判官/复核。**

- **为什么分两条线**：飞书文档只能关键词搜（平台限制，改不了），召回有天花板；而**我们自己上传的知识库是"自有数据"，能完整落地稠密向量召回**——"测试环境"能搜到写"dev/pre"的文档。所以**平台管不了的那部分召回质量，我在自建库这条线上自己补齐**。

---

## 核心技术点（白话）

1. **为什么要两道闸，而不是只看向量分**：实测过，向量相似度**分不开相关和无关**——相关的 0.55~0.76，无关的也有 0.25~0.55，在 0.55 附近重叠。所以向量只做"粗筛别漏"，真正判"答不答得上"交给 **LLM 判官**（逐条打 0~3 分）。
2. **阈值是实测标定的，不是抄经验值**：网上常说余弦设 0.7，那是别的模型的数。我量了本模型分布，真答案落在 0.55~0.66，**设 0.7 会误杀真答案**，所以定 0.40。
3. **对抗式复核**：判官约 90~95% 准，偶尔对"沾边"心软给 2 分。判 3 直接信任，**只对判 2 的边界档换个"怀疑者"口吻再严判一遍**，拿不准就毙。多维审计里误报从 13→0。
4. **自建库混合召回**：BM25 保字面、向量保语义、RRF（倒数排名融合）并两路，字面和语义都不漏。**实测：内容只写"dev/pre"，用"开发/预发布环境"能召回**——证明稠密语义召回真的работает。
5. **结构感知切块**：Q&A、小节各自独立成块，避免答案被无关内容稀释。
6. **答案落地要 grounded**：只喂精准段、`[n]` 角标标来源、文档 `#block_id` 深链、聊天定位到具体那条；**库里没有就明说没有，绝不硬编**。
7. **答案置信度分级**：复用判官分——入选档最高 3 分标**高置信**、只有压线 2 分标**中置信**（提醒用户点开来源核对），并显示"N 篇佐证"。把"反幻觉"做成看得见的信号。

## 文档摄入（零依赖解析，一个独立亮点）

上传的 Word/Excel/PPT/PDF/图片，**服务端解析成文本再建索引**，且尽量零依赖：
- **Office（docx/xlsx/pptx）**：本质是 ZIP+XML，用 Node 内置 `zlib` 手写最小 ZIP 读取（走中央目录 + inflateRaw）+ 按文档顺序抽 `<w:t>`/`<a:t>`/`<t>` 文本，**零第三方库、零 key**。
- **文本型 PDF**：手写 FlateDecode 解流 + 抽文本算子（`(str)Tj`、`[..]TJ` 用大负位移补词间空格、`Td/T*` 当换行），**零依赖、零 key**。实测 34 万字 PDF，标题/空格/换行都对。
- **图片 / 扫描件 PDF**：本质是"图"，走外部 OCR API；**没配 OCR key 时只提示这一类需要配置、不影响其它文件上传**。
- **设计原则**：**缺哪个 key 只挡哪个功能，且只在真正用到时才提醒**，不因一个 key 缺失就全局禁用。

## 平台边界怎么突破（"官方说没有"的两次攻坚）

这两个是最能讲的工程故事——**"文档说没有 ≠ 能力不存在，实测才是唯一判据"**：

1. **消息定位到具体某条**：官方文档 + 技术人员都说第三方没有。但接口每条消息都返回 `message_position`、客户端自己能跳转高亮——推断深链能吃一个**没写进文档的 `position` 参数**，`client/chat/open?openChatId=X&position=N` 真机实测果然跳转并高亮。
2. **以"用户本人身份"发消息（一键转发）**：想做"分享给同事"，起初以为只有机器人能发（那样落在"对方与机器人的私聊"、不是我的名义）。实测报错 `99991679` 点名要 `im:message`，查官方文档确认发消息接口**支持 user_access_token**、用户身份权限是 `im:message` + `im:message.send_as_user`（点号）。开通 + 重登后实测 **`sender_type=user`**——真的以本人身份发出。**分享的本质=以我账号把答案导出成云文档 + 把链接/卡片以我身份发给指定群/人**，不走机器人。

## 工程难点（现象 → 根因 → 怎么解）

1. **大文档精准段被丢**：切块超上限"从头按位置砍"，含答案的段被砍、整篇分数虚低 → **先按词面相关度排序再砍**。
2. **关键词抽歪导致召不回**：LLM 抽词会丢词/加词 → **关键词 + 原问题双路各搜一次**兜底。
3. **聊天有问无答**：命中的常是"问"、答在后面几条 → **补命中消息前后几条再判**（治"喂给判官的料"，不换算法）。
4. **缓存回放旧错答案**：FAQ 秒答放出过期错答案、还害我"自测过但浏览器错" → **停用答案缓存**，核心必走真实检索。
5. **精排出错反而全放出来**：fail-open → 改 **fail-closed**，宁可留空不硬塞。
6. **垃圾消息污染**：机器人/日志泄漏进群 → **按"是不是真人发的"从根上过滤**。
7. **判官 prompt 过拟合**：具体 case 写进提示词 → **重写成通用原则** + 版本号作废旧缓存。
8. **向量层静默降级成词法**：嵌入耦合了"用户选的对话厂商"、残留默认厂商没配 key → **嵌入与对话模型解耦**，一律 GLM embedding-3。
9. **空召回时"今天周几"被当没找到**：空召回直接短路成"未找到" → 改成走通用回答；再加**轻分类器 `classifyNeedsDoc`** 分流：常识/寒暄直接答，只有"需要公司内部资料却没找到"才引导关注公众号。

## 产品 / 信任层的设计（不只是检索）

- **答不了的兜底**：确实没找到时，引导"关注公众号留言 / 一键把问题提交给作者"，问题进反馈库成为补料清单。
- **点踩闭环 → bad-case**：点踩后追问"哪里不对"（选原因+补充），沉淀成"待改进"清单，形成质量飞轮，也反哺评测集。
- **澄清反问**：**完全没对象**的问题（"有问题吗""进度呢"）先反问补全；带具体名词的一律直接检索、不打扰（保守，避免烦人）。
- **冲突检测**：≥2 篇入选来源时，查是否**实质矛盾**（数值/结论/步骤不一致，而非详略不同），有则在参考区上方黄条点明，让用户自行甄别。
- **时效性标注**：参考卡显示"3 周前/2 个月前更新"，超 180 天标"可能过期"。
- **身份类问题**（你是谁/谁开发的）→ 固定介绍 + 引导公众号。

## 安全 · 隔离 · 多租户（面试常追问）

- **数据隔离**：对话按 `ownerOpenId` 存取且有 **IDOR 校验**（拿到别人对话 id 也读不到）；检索一律用**用户自己的飞书 token**，飞书按其本人权限返回——**权限天然在读取步骤被强制**。
- **Key 模型**：每人在设置里填**自己的 LLM key**（存各自会话、绝不外传前端）；没填只在发起提问那一刻懒提醒。对外部署把默认 key 留空即可**保证自己的 key 不被别人消耗**。
- **开源规范**：所有密钥走 `.env`（已 gitignore），`.env.example` 写明"自带飞书应用 + 自带 key + 默认留空"。
- **多租户认知**：飞书**自建应用是"租户绑定"的**（只能本企业用），所以开源要每个部署者建自己的应用；要做"一个域名跨企业开箱即用"得走**商店应用（ISV）**——这是规模化的下一步。

## 广度（撑起系统的那些）
多用户飞书 OAuth + 按人权限隔离、SSE 流式、多源接入（云盘/知识库/表格/会话/**本地上传库**）、飞书群机器人（AES 事件解密 + 按发消息人权限作答）、**导出到飞书云文档 / 以本人身份一键转发卡片**、定时主动推送、提问看板（含 bad-case）、开发者调参面板、**检索可解释**（召回数/向量分/判官分全摊开）。

---

## 质量怎么保障
- **确定性评测**：固定题目，量化召回率/干净率，反复跑不费 token。
- **对抗式多维审计**：一批各类问题跑真实链路 + 独立严格评审逐条判"展示的每条是不是真相关"，**把'出现无关文档'这个失败做成回归测试**。一轮把误报 13→0。

## 面试可能被问的角度（自检清单）

- **系统设计**："画一下架构" → 两条检索线合流 + 两阶段精排那张图；讲清"召回要全、精排要准"的分工。
- **检索为什么这么设计**：向量分布重叠 → 判官；判官会心软 → 对抗复核；单路召回会漏 → 双路/混合 + RRF。每一步都有"上一步的不足"驱动。
- **数据驱动**：阈值 0.40 是量分布量出来的，不是抄 0.7；误报 13→0 是审计跑出来的。**能拿数字说话**。
- **平台限制怎么破**：消息定位 `position`、以用户身份发消息 `send_as_user`——都是"文档说没有、实测拿下"。体现工程韧性和"不轻信文档、只信实测"。
- **权衡**：为什么零依赖（吃透每一环、易审计、部署简单）；Office/PDF 手写解析 vs 引库的取舍；精度 vs 召回冲突时坚定选精度。
- **产品思维**：反幻觉怎么变成用户能感知的（置信度、兜底、拒答）；质量飞轮（点踩→bad-case→补料）；增长（工程故事连载 + 内核开源引流）。
- **安全/规模化**：隔离与 IDOR、按人 token 的权限模型、key 不外漏、自建应用 vs 商店应用、单机 JSON → 多实例共享存储的演进。
- **难点复盘**：缓存回放旧错答案那次——"自测过但线上错"，教训是**验证一定走真实链路，别被缓存蒙**。

---

## 我对这个项目的思考
- **精度和召回冲突时，坚定选精度**：宁可漏、也不能错。信任一崩，产品就废了。
- **平台是有边界的，但边界之外还有实测空间**：飞书只有关键词、没有语义 API——所以我在**自建知识库这条线**把稠密语义召回补齐；而 `position`、`send_as_user` 证明"官方文档不是能力的边界"。
- **沉淀成方法论**：关键参数用数据标定、验证走真实链路、修完 bug 抽象成通用原则并纳入回归、缺 key 只挡对应功能。
