# 检索现状、飞书 API 边界与商用化路线

## 核心检索还卡在哪（白话）

1. **飞书关键词搜索的召回天花板（已被真实重复测试证伪为商用主链路）**：飞书只做字面匹配，且同一问题的有限 Top N 会漂移。它可以保留为在线兜底，但“只用关键词就够用”的旧结论不再成立。
2. **自有数据这侧已把语义召回补齐**：**用户上传的知识库**是我们自己的数据，做了全套稠密召回（切块+embedding+BM25/向量 RRF）。实测内容只写"dev/pre"、用"开发/预发布环境"也能召回。**平台管不了的召回，我在自建库这条线上解决了。**
3. **上传文件已能解析入库**：docx/xlsx/pptx/文本PDF 零依赖解析；图片/扫描件走 OCR（懒提醒填 key）。
4. **聊天一问一答**：已改为来源感知链路。向量用“命中消息”衡量召回强度，判官读取结构化的“命中消息 + 后续回复”；回复限定时间窗，并对重叠会话窗口去重。不能再把聊天当普通文档段落截断后评分。
5. **判官稳定性**：温度设为 0、评分持久化缓存、边界档二次复核；判官不可用时显式降级到确定性的向量/词法结果，不再把所有候选伪造为 3 分。实际准确率必须由来源分层评测集持续度量，不能在没有标注数据时声称“接近 0 误报”。

一句话：**增量索引只建设在用户主动上传的知识库；飞书文档和聊天保持当前用户权限下的实时召回，不做全量离线索引。**详见《实时事实检索与缓存架构》。

## 飞书 API 的真实边界（实测 / 官方确认，不是猜）

| 想要的能力 | 结论 |
|---|---|
| 文档语义 / 向量搜索 | ❌ 没有（两个搜索接口都是关键词） |
| 文档 embedding 接口 | ❌ 没有 |
| 消息深链（定位到具体某条消息） | ✅ **能**——`applink client/chat/open?openChatId=X&position=N`，官方文档没写，实测有效 |
| 以用户本人身份发消息 | ✅ **能**——`im:message` + `im:message.send_as_user`，实测 `sender_type=user` |
| 上传 xlsx 的内容检索（飞书侧） | ❌ 只索引文件名（故自有数据走我们自建库） |

## 走向商用怎么做（按优先级）

1. ✅ **自建知识库语义召回**（已完成）：切块+embedding+BM25/向量 RRF，接入主链路、实测语义召回有效。
2. **上传知识库增量更新**：文档 revision + chunk hash，只向量化变化块；飞书文档和聊天继续实时召回。
3. ✅ **PDF / Office 解析入库**（已完成）：零依赖解析文本；图片/扫描件走 OCR（待接厂商）。
4. **精度持续收尾**：建立 document/chat 分层金标集，至少统计 Recall@K、MRR、Precision@K、拒答准确率；每个版本做重复运行稳定性测试。
5. **压延迟、上规模**：自建库 chunk 量大时由暴力余弦换 ANN；加安全的内容寻址缓存、批量嵌入、并行化；单机 JSON → 多实例共享存储。
6. **质量工程化**：评测 + 审计接入 CI；线上记录来源、召回查询、候选池、向量分、判官分、降级原因和最终引用，并按来源监控。
7. **权限与安全**：按人隔离（已含 IDOR 校验）、每人自带 key、生产留空默认 key；跨企业开箱即用需做商店应用（ISV）。

## 一句话结论
当前链路已经具备可试运行的检索骨架，但还不能仅凭少量人工案例宣称“达到商用”。上线门槛应是：来源分层金标集达标、重复运行抖动达标、判官/向量服务故障演练通过、线上可观测与反馈闭环完备。
