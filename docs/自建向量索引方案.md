# 自建知识库向量索引 — 方案与现状（已落地）

## 决策边界（2026-07-23 修订）
- **本文件只描述用户上传知识库的已实现索引**。此前“飞书关键词搜索够用、无需索引”的结论已被真实重复测试推翻，不能再作为商用架构决策。
- 飞书文档与聊天不做全量离线索引，始终使用当前用户 token 实时召回；增量索引仅用于用户主动上传、系统能控制版本的知识库。详见《实时事实检索与缓存架构》。
- **只给"用户上传的知识库"建索引**：这是我们自己的数据，在这条线上做全套稠密召回。
- 于是形成**两条检索线**：飞书（关键词）+ 自建库（BM25+向量），各自召回后合并、共用同一套精排/判官。

## 已实现（server/kb.js）
1. **上传即建索引**：切块（500 字 / 100 重叠）→ 每块用 embedding-3 取向量存进该用户的库（按 openId 隔离的 JSON）。
2. **混合召回 `searchKbHybrid`**：查询时 **BM25（稀疏/字面）+ 向量余弦（稠密/语义）** 两路排名，用 **RRF（倒数排名融合）** 合并，按文档去重返回 top 篇。
3. **接入主链路**：在 rag.js 里与飞书检索、会话检索**并行召回**，合并候选池后进统一的向量重排 + LLM 判官 + 对抗复核。
4. **实测验证**：上传内容只写"dev/pre 环境"，用"开发/预发布环境怎么区分"查询——**稠密向量成功召回**（字面不匹配也召回），证明语义召回基座扎实。
5. **增量更新**：文档保存 revision/content hash/chunk hash；更新时复用未变化块，只向量化变化块；索引失败保留旧版本。
6. **权限与并发**：每个 openId 独立存储，API 对跨用户 id 返回不存在；同一用户写操作串行并原子落盘，expectedRevision 防止旧页面覆盖新版本。

## 架构
```
上传：文件 → 解析(parse.js) → 切块 → embedding-3 → 存向量(chunk向量 + 元数据，按openId)
在线：问题 → BM25 + 向量ANN(现为暴力余弦) → RRF融合 → 与飞书/会话召回合并 → 重排/判官 → 答案
```

## 影响与规模化
- **延迟**：暴力余弦在中小库（万级 chunk 内）几十~百 ms，够用。
- **规模化拐点**：单用户上传量很大（十万级 chunk）时，把暴力余弦换成专用向量库/ANN（那时才引入依赖）。
- **成本**：只有上传时的嵌入调用（单价低）。
- **无向量兜底**：没配 embedding key 时上传只建 BM25、检索仍可用（降级为纯字面）。

## 待办（非阻塞）
- 图片/扫描件 OCR 接具体厂商（`ocrImage` 是通用形状，待对接）。
- 规模化时的 ANN + 缓存。

---
**结论**：用户上传知识库使用可更新的增量混合索引；飞书文档与聊天是独立的实时事实源，不纳入离线索引。
