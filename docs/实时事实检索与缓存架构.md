# 实时事实检索与缓存架构

版本：1.0（2026-07-23）  
状态：目标架构与当前差距说明；未标记“已实现”的能力不得作为线上承诺。

## 1. 服务定义

本项目是一个**按提问人飞书权限检索实时企业事实，并给出可核验引用的 RAG 服务**，不是普通聊天机器人，也不是“相同问题返回相同答案”的 FAQ 机器人。

成功标准按优先级排序：

1. 不越权：候选、正文、引用都在当前用户权限内。
2. 不陈旧：状态、进度、人员、排期等问题优先使用最新可核验事实。
3. 不编造：结论必须由实际展示的证据支撑；无证据就拒答或明确资料不足。
4. 找得全：文档正文与聊天问答窗口都能进入候选池。
5. 排得准：直接答案、更新状态和完整上下文优先于关键词相似问题。
6. 可运营：失败自动进入质量工作台，人工标注后进入冻结金标集。
7. 可用：在前述目标成立后，再优化首字、总耗时和模型成本。

## 2. 数据必须分层

| 数据类型 | 变化特点 | 在线策略 | 是否允许答案秒答 |
|---|---|---|---|
| 飞书聊天 | 高频增量、可撤回/编辑、答案依赖上下文 | 始终使用当前用户 token 实时召回并补问答窗口，不建离线索引 | 否 |
| 飞书业务文档 | 会更新、移动、删除、权限变化 | 始终使用当前用户 token 实时搜索和读取，不建离线索引 | 默认否 |
| 用户上传知识库 | 系统可控制版本 | 按所有者隔离；上传/更新只重建变化块 | 默认否 |
| 人工发布固定问答 | 人工确认、版本明确 | 独立“已发布知识答案”集合 | 可以，但必须校验版本与权限 |
| 意图/路由 case | 不是业务事实 | 规则/分类器/金标集 | 只缓存路由结果，不缓存业务答案 |

“问过多次”不能让生成答案自动升级为固定问答。固定问答只能由人工发布，并保留负责人、有效期、来源、版本和撤回能力。

## 3. 生产检索架构

### 3.1 当前 MVP

- 飞书文档：每次请求调用关键词搜索，再在线读正文。
- 飞书聊天：每次请求调用消息搜索，命中消息携带后续回复形成问答窗口。
- 用户上传知识库：BM25 + embedding 向量双路召回，RRF 融合。
- 多来源候选：向量粗筛、当前模型相关性判定、证据质量排序、生成与引用。

这个 MVP 保持了飞书原生权限，但飞书搜索结果会漂移，无法保证同一最新文档稳定进入有限读取池。2026-07-23 同一错别字状态问题的真实重复测试已复现：冷测命中 2026/07/15 周报，随后热测未召回该周报。因此该链路目前只能称“可运行基线”，不能称商用稳定召回。

### 3.2 当前确定的目标架构

采用“**上传知识库增量索引 + 飞书文档实时检索 + 飞书聊天实时召回**”三条独立数据线：

1. 用户上传知识库按 `openId` 独立存储，文档包含 revision、content hash、chunk hash 和 embedding identity。
2. 更新上传文档时复用文本和 embedding identity 均未变化的块，只对新增或变化块调用 embedding。
3. 索引构建完成后才原子替换旧版本；失败保留旧正文和旧 revision。并发更新使用 expectedRevision 防覆盖。
4. embedding 端点或模型变化后旧向量不参与相似度计算；用户可显式重建本人全部索引。
5. 飞书文档不做离线索引，每次查询都使用当前用户 token 执行搜索和正文读取。
6. 飞书聊天不做离线索引，每次查询都使用当前用户 token 搜索消息，并动态补齐问题前后的会话窗口。
7. 上传库权限由所有者文件分区和 API owner 校验共同保证；飞书权限由当前用户 token 在搜索和读取两次强制。

这一架构不会用缓存掩盖飞书搜索抖动。飞书在线召回的稳定性仍必须通过多查询、来源感知候选预算、时效席位和重复运行评测持续控制。

## 4. 来源感知召回

### 4.1 文档

- 标题、正文、章节标题分别建字段。
- 状态问题保留时效席位，但日期只能来自内容时间或可靠元数据。
- 同一文档只保留最相关的若干块；引用仍指向原文与具体块。
- 更新后只重建变化块，revision 改变后旧 embedding 自动失效。

### 4.2 聊天

- 命中问句时带同一会话后续回复；命中回答时补前文问题。
- 窗口按 reply/thread 关系优先，时间邻近只是没有结构信息时的兜底。
- 编辑、撤回、纠正消息要进入窗口版本；重叠 message_id 的窗口去重。
- 状态类回答同时保存消息发生时间，旧计划不得冒充当前事实。

### 4.3 固定问答与意图 case

固定问答应是独立数据模型，而不是普通 RAG 答案缓存：

```text
PublishedAnswer {
  id, tenant_id, intent_examples[], canonical_question,
  answer, source_refs[], source_revision_fingerprint,
  acl_scope, owner, published_at, expires_at, status
}
```

命中后仍要检查租户、用户权限、有效期以及所有来源 revision。任一不匹配就回退实时 RAG。人工修改或撤回后立即失效。

## 5. 缓存策略

### 5.1 允许

- Embedding：`endpoint + model + content_hash`，内容或模型变化自动失效。
- 文档正文对象：`tenant + token + revision` 的内容寻址缓存；使用前先获得可靠 revision，不能仅靠 TTL 猜测未更新。
- 查询规划与相关性判定：短 TTL，key 含模型端点、模型、prompt/算法版本、问题和证据 hash；点踩可定向失效。
- OAuth/app token：只按官方有效期缓存并提前刷新。
- 人工发布固定问答：只按第 4.3 节的版本与权限规则命中。

### 5.2 禁止

- 自动缓存任意生成答案。
- 缓存飞书搜索结果并把它当成最新事实。
- 仅用“问题文本 + 用户”作为答案缓存 key。
- 文档更新后继续使用旧正文、旧引用或旧 embedding。
- 跨用户复用未经 ACL 过滤的候选集或答案。

## 6. 在线链路

```text
问题
 → 查询理解（原词始终保留，模型候选需语料校验）
 → 并行召回
    ├─ 用户上传知识库增量混合索引
    ├─ 飞书文档实时搜索与读取
    └─ 飞书聊天实时搜索与上下文窗口
 → 上传库 owner 校验 / 飞书当前用户 token 权限校验
 → 来源感知去重、向量粗排
 → 当前模型分批相关性判定
 → 直接性/完整性/时效/冲突排序
 → 自适应主证据 + 全量更多相关
 → 仅基于主证据生成，引用编号严格一致
 → 自动记录轨迹与反馈，进入质量工作台
```

## 7. 新鲜度与稳定性 SLO

在真实数据和压测未完成前，以下只能作为验收目标，不能写成已达成：

- 上传文档变化块重建耗时有 p50/p95；失败回滚率和 revision 冲突率可观测。
- 上传文档删除后立即不可召回；飞书删除或撤权由下一次实时搜索/读取生效。
- 同一冻结数据、同一配置重复 5 次，目标证据 Recall@K 和主证据集合达到约定一致率。
- 在线补查失败时显式标记降级，不能静默把旧结果当最新。
- 30 次以上代表性请求分别报告冷/热 p50、p95、失败率、首字和总耗时。

## 8. 当前已验证与未验证

### 已验证

- 主问答和定时追踪不再读写生成答案缓存。
- 生产飞书搜索与正文读取没有结果缓存；fixture 只在显式离线评测环境生效。
- Embedding key 已包含端点、模型和正文 hash。
- 模型决策缓存默认关闭；显式启用时有 TTL、版本和点踩失效代次，准确率测试仍可强制绕过。
- 上传知识库已有 revision、变化块向量复用、模型身份失效、原子写入、失败回滚、并发串行化和 owner 隔离测试。
- 聊天候选保留命中消息与后续回复；重叠窗口去重。
- 六断点无横向溢出，“更多相关”有可测动画与省略号。

### 未达到商用门槛

- 真实飞书在线搜索存在候选漂移，最新资料稳定召回尚未达标。
- 人工发布固定问答的数据模型、审批与来源版本校验尚未实现。
- 人工金标数量不足，尚无足够样本证明 Recall@K、Precision@K、答案正确率和 p95 达标。

## 9. 实施顺序

1. 持续回归上传知识库增量索引、revision、失败回滚和所有者隔离。
2. 冻结 document/chat/uploaded 分层金标，重复测试飞书在线搜索稳定性。
3. 优化飞书文档与聊天的实时查询扩展、候选预算和来源感知排序。
4. 实现人工发布固定问答，严格版本和权限校验。
5. shadow 对比算法版本，不影响用户；达标后灰度并保留回滚。
